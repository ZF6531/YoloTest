## 1. 时序同步问题

### 问题描述
视频解码后的 PTS（Presentation Time Stamp）与音频的播放时钟不一致，导致音画不同步。原因可能包括：
- 源文件本身时间戳错乱
- 转码或剪辑后未重新校准时间基
- B 帧导致解码顺序与显示顺序不一致

### 解决方法

| 方法 | 说明 |
|------|------|
| **重新校准时间戳** | 使用 `ffmpeg -fflags +genpts` 重新生成缺失或错误的 PTS |
| **统一时间基** | 转码时强制指定 `setpts=PTS-STARTPTS` 和 `asetpts=PTS-STARTPTS`，让所有流从 0 开始对齐 |
| **音频主时钟同步** | 播放器以音频时钟为主轴，视频帧根据 PTS 提前或延后渲染（加速或等待） |
| **外部时钟同步** | 直播场景使用系统时钟（system clock）作为基准，动态调整音视频的播放速率 |

### FFmpeg 示例
```bash
# 修复时间戳错乱
ffmpeg -fflags +genpts -i input.mp4 -c copy output_fixed.mp4

# 剪辑后重新对齐音画
ffmpeg -ss 00:01:00 -i input.mp4 -t 30 -vf "setpts=PTS-STARTPTS" \
       -af "asetpts=PTS-STARTPTS" -c:v libx264 -c:a aac output.mp4
```

## 2. 延迟问题

### 问题描述
从采集到播放的端到端延迟过大，常见于直播、连麦、监控场景。延迟来源包括：
- 编码器缓冲（B 帧、lookahead）
- 网络传输协议开销（HLS 切片、TCP 重传）
- 播放器缓冲（jitter buffer、解码缓冲）

### 解决方法

#### 2.1 编码侧降低延迟
| 方法 | 说明 |
|------|------|
| **关闭 B 帧** | 使用 `-bf 0`，避免双向预测带来的帧重排延迟 |
| **降低 GOP 大小** | 设置 `-g 30`（1 秒 GOP），减少编解码缓冲和随机访问等待 |
| **使用低延迟预设** | x264 的 `-tune zerolatency` 专为实时通信优化 |
| **减少 lookahead** | 设置 `-rc-lookahead 0` 或降低至 10 帧以内 |

#### 2.2 网络侧降低延迟
| 方法 | 说明 |
|------|------|
| **选择低延迟协议** | 直播推流用 RTMP/SRT/RTSP，实时互动用 WebRTC，避免 HLS/DASH |
| **使用 UDP 而非 TCP** | 对实时性要求高的场景，UDP 避免了 TCP 的队头阻塞和重传等待 |
| **减少切片时长** | HLS  unavoidable 时，将切片时长从 10s 缩短至 2~3s |

#### 2.3 播放侧降低延迟
| 方法 | 说明 |
|------|------|
| **减小 jitter buffer** | 降低音频缓冲时长，但会增加卡顿风险 |
| **硬解优先** | 硬件解码器通常比软解延迟更低 |
| **预渲染帧数控制** | 限制播放器解码缓冲队列深度 |

### FFmpeg 低延迟推流示例
```bash
ffmpeg -i input -c:v libx264 -preset ultrafast -tune zerolatency \
       -x264opts "nbframes=0:vbv-maxrate=4000:vbv-bufsize=200" \
       -g 30 -bf 0 -c:a aac -f flv rtmp://server/live/stream
```

## 3. 低带宽下的稳定性

### 问题描述
上行或下行带宽不足时，视频出现频繁卡顿、码率突增导致缓冲区排空、连接断开等问题。

### 解决方法

#### 3.1 编码侧：动态码率控制
| 方法 | 说明 |
|------|------|
| **ABR（Adaptive Bitrate）编码** | 服务端同时输出多路码率（720p@1.5Mbps, 480p@800kbps），播放器根据带宽切换 |
| **动态调整分辨率/帧率** | 带宽下降时自动降分辨率或降帧率，保证基础可用性 |
| **限制峰值码率（VBV）** | 使用 `-maxrate` 和 `-bufsize` 控制码率波动，避免瞬间超过带宽上限 |

#### 3.2 网络侧：前向纠错与重传
| 方法 | 说明 |
|------|------|
| **FEC（Forward Error Correction）** | 发送冗余包，接收端在少量丢包时无需重传即可恢复 |
| **NACK / RTX** | WebRTC 中通过 NACK 请求重传关键帧或音频包 |
| **SRT 协议** | SRT 内置 ARQ 重传和拥塞控制，适合弱网直播 |

#### 3.3 播放器侧：缓冲策略
| 方法 | 说明 |
|------|------|
| **自适应缓冲** | 根据当前网速动态调整缓冲水位，网速慢时增加缓冲深度 |
| **快速降档** | 检测到带宽骤降时，立即切到更低码率档位 |

### FFmpeg 多码率输出示例
```bash
ffmpeg -i input \
  -map 0:v:0 -s:v:0 1920x1080 -b:v:0 4000k -maxrate:v:0 4500k -bufsize:v:0 8000k \
  -map 0:v:0 -s:v:1 1280x720  -b:v:1 2000k -maxrate:v:1 2200k -bufsize:v:1 4000k \
  -map 0:v:0 -s:v:2 854x480   -b:v:2 800k  -maxrate:v:2 900k  -bufsize:v:2 1600k \
  -map 0:a:0 -c:a aac -b:a 128k \
  -var_stream_map "v:0,a:0 v:1,a:0 v:2,a:0" -master_pl_name master.m3u8 \
  -f hls -hls_time 4 -hls_playlist_type vod output_%v.m3u8
```

## 4. 网络波动与自适应

### 问题描述
移动网络、Wi-Fi 切换、基站切换等导致 RTT 和丢包率剧烈波动，引发卡顿和延迟累积。

### 解决方法

| 方法 | 说明 |
|------|------|
| **GCC（Google Congestion Control）** | WebRTC 默认拥塞控制算法，基于延迟和丢包双信号动态调整发送码率 |
| **BBR 拥塞控制** | 相比传统 CUBIC，BBR 能更快探测可用带宽，减少 bufferbloat |
| **动态帧率/分辨率切换** | 发送端根据 GCC/BBR 反馈的估计带宽，实时调整编码参数 |
| **QoS 标记（DSCP）** | 在网络层为音视频包标记高优先级，减少路由器排队丢弃 |
| **多路径传输（MPTCP/MPQUIC）** | 同时利用 Wi-Fi 和 4G/5G 链路，单条链路波动时无缝切换 |

## 5. 丢帧与卡顿

### 问题描述
- **丢帧（Frame Drop）**：解码器或渲染器来不及处理，主动丢弃部分帧
- **卡顿（Stutter/Jank）**：播放器缓冲区为空，画面暂停等待数据

### 原因分析
1. **解码性能不足**：高分辨率视频（4K/8K）超出设备解码能力
2. **渲染线程阻塞**：UI 线程卡顿导致 Surface 未能及时提交
3. **网络抖动**：数据包到达不规律，周期性缓冲下溢

### 解决方法

| 方法 | 说明 |
|------|------|
| **启用硬解** | 使用 GPU/专用解码单元（DXVA/VAAPI/VideoToolbox/MediaCodec）处理高码率视频 |
| **跳过 B 帧 / 非参考帧** | 解码压力过大时，优先丢弃 B 帧和 non-reference P 帧，保证基础流畅度 |
| **降低播放分辨率** | 软解 4K 卡顿的设备，可请求服务端提供 1080p 甚至 720p 流 |
| **优化渲染链路** | 使用独立渲染线程、减少 GPU 过度绘制、开启 VSync |
| **增大播放缓冲** | 点播场景适当增加 5~10 秒缓冲，吸收网络抖动 |
| **帧率平滑（Frame Pacing）** | 根据显示器刷新率动态调整帧提交时机，避免 uneven 帧间隔 |

## 6. 画质退化问题

### 问题描述
压缩过度、多次转码、分辨率拉伸、低码率下出现马赛克、色带、模糊、块效应。

### 解决方法

| 问题 | 解决方法 |
|------|----------|
| **块效应（Blocking）** | 开启去块滤波器（deblock），H.264 的 `-deblock` 参数；或转码时使用 `-vf "pp=hb/vb/dr/al"` |
| **色带（Banding）** | 提高编码位深（10bit），或使用 `-vf "gradfun"` 梯度平滑滤镜 |
| **模糊/细节丢失** | 降低 CRF 值（提高质量），增加码率，或使用更高效的编码器（H.265/AV1 同等码率画质更好） |
| **多次转码损失** | 尽量避免反复有损压缩，中间环节使用 mezzanine 格式（ProRes、DNxHD）或无压缩 |
| **拉伸失真** | 保持原始宽高比缩放，避免非整数倍拉伸；用 Lanczos/bicubic 代替 nearest neighbor |

### FFmpeg 画质优化示例
```bash
# 使用更慢预设提升压缩效率（相同码率画质更好）
ffmpeg -i input.mp4 -c:v libx264 -preset slow -crf 23 -c:a copy output.mp4

# 去除色带
ffmpeg -i input.mp4 -vf "gradfun" -c:v libx264 -crf 20 output.mp4

# 10bit 编码（减少色带，提升暗部细节）
ffmpeg -i input.mp4 -c:v libx265 -preset medium -crf 22 -pix_fmt yuv420p10le output.mp4
```

## 7. 音画不同步

### 问题描述
虽然属于同步问题的一种，但音画不同步是用户感知最强烈的问题，需要单独讨论。常见原因：
- 采集端音视频采样时钟不一致（drift）
- 播放器处理速度差异（视频渲染慢于音频播放）
- 视频经过滤镜/重采样后时间戳未修正

### 解决方法

| 场景 | 解决方法 |
|------|----------|
| **源文件不同步** | `ffmpeg -itsoffset 0.5 -i video.mp4 -i audio.mp4 -c:v copy -c:a copy output.mp4` 手动偏移对齐 |
| **播放器不同步** | 实现音视频同步模块：以音频为主时钟，视频帧提前/延后渲染；差值过大时丢帧或重复帧 |
| **时钟漂移** | 长时直播场景，定期计算音视频 PTS 差值，动态微调播放速率（±2% 以内） |
| **采集端不同步** | 使用同一主时钟驱动音频和视频采集设备，或后期通过时间戳拉伸补偿 |

## 8. 首屏打开慢

### 问题描述
用户点击播放后，需要等待数秒才能看到第一帧画面。原因通常是：
- 播放器需要下载完整个 moov 头（MP4 的索引信息在文件尾部）
- GOP 过大，需要等待 I 帧才能开始解码
- DNS 解析、TCP/TLS 握手耗时

### 解决方法

| 方法 | 说明 |
|------|------|
| **moov 前置（Fast Start）** | 使用 `-movflags +faststart`，将 moov 原子移动到文件开头 |
| **减小 GOP** | 设置 1~2 秒 GOP，确保播放器尽快遇到 I 帧 |
| **服务端发送关键帧** | 直播场景，用户加入时服务器立即发送最近的 I 帧（IDR） |
| **预连接与 DNS 缓存** | App 启动时预热 TCP 连接和 DNS 解析结果 |
| **预加载（Prefetch）** | 首屏前预下载前几秒数据，实现"秒开"体验 |

### FFmpeg Fast Start 示例
```bash
ffmpeg -i input.mp4 -c:v libx264 -g 30 -movflags +faststart output.mp4
```

## 9. 花屏与绿屏

### 问题描述
画面出现块状错乱、颜色异常（绿色/粉色）、条纹或完全破碎。

### 原因与解决

| 现象 | 原因 | 解决方法 |
|------|------|----------|
| **花屏（宏块错乱）** | 丢包导致参考帧损坏、P/B 帧依赖错误 | 开启 FEC、请求 IDR 关键帧、关闭错误传播 |
| **绿屏/粉屏** | 像素格式不匹配（如 NV12 当 YUV420P 处理）、alpha 通道缺失 | 检查像素格式设置，显式指定 `-pix_fmt` |
| **顶部/底部条纹** | 分辨率对齐问题（如 1080p 实际高度 1088，需要 crop） | 使用 `-vf "crop=1920:1080:0:0"` |
| **解码器崩溃花屏** | 硬件解码器遇到 unsupported profile/level | 回退到软解，或降低编码 profile |

## 10. 回声与噪声

### 问题描述
实时通话中，远端声音从本地扬声器播放后又被麦克风采集回去，形成回声；环境噪声、电流底噪影响语音清晰度。

### 解决方法

| 问题 | 解决方法 |
|------|----------|
| **回声消除（AEC）** | 使用 WebRTC AEC3、Speex AEC 等算法，建立远端参考信号与近端采集信号的抵消模型 |
| **噪声抑制（NS）** | WebRTC NS、RNNoise（基于 AI）等算法，实时过滤背景噪声 |
| **自动增益控制（AGC）** | 动态调整麦克风输入音量，避免声音过大削波或过轻听不清 |
| **硬件回声消除** | 部分手机/耳机自带 AEC，可优先调用 |
| **双工模式选择**** | 多人通话建议使用耳机或全向麦+扬声器组合，降低声学回路增益 |

## 11. CPU/GPU 过载与发热

### 问题描述
高分辨率实时编码或复杂滤镜处理导致 CPU/GPU 占用过高、设备发热、续航下降，甚至触发系统降频。

### 解决方法

| 方法 | 说明 |
|------|------|
| **硬件编码优先** | 移动端用 MediaCodec/VideoToolbox，PC 端用 NVENC/Quick Sync，大幅降低 CPU 负载 |
| **降低编码预设档位** | x264 从 `veryslow` 降到 `fast` 或 `ultrafast`，牺牲少量压缩效率换取性能 |
| **分辨率/帧率降级** | 发热时主动降至 720p@30fps 或 480p@30fps |
| **关闭非必要滤镜** |  beauty、动态贴纸等 GPU 滤镜按需开启 |
| **后台降级策略** | App 切后台时暂停视频编码，或仅编码音频 |

## 12. 兼容性问题

### 问题描述
某些视频在某些设备或浏览器上无法播放、有音无画、有画无音、黑屏等。

### 常见兼容性问题与解决

| 问题 | 原因 | 解决方法 |
|------|------|----------|
| **Safari 无法播放 MP4** | 使用了 High 4:4:4 Predictive profile 或音频为 AC3 | 转码为 Baseline/Main profile + AAC |
| **Chrome 无法播放 HEVC** | Chrome 对 HEVC 支持有限（需硬件和许可） | Web 场景优先使用 H.264 或 AV1 |
| **老设备无法播放 10bit 视频** | 硬件解码器不支持 10bit | 提供 8bit  fallback 版本 |
| **Android 软解 H.265 卡顿** | 中低端机无 HEVC 硬解 | 对 Android 提供 H.264 主版本 |
| **无声音** | 音频采样率/声道布局不被设备支持 | 统一重采样到 48kHz stereo |

### 兼容性推荐配置
```bash
# Web 通用兼容格式（H.264 + AAC）
ffmpeg -i input.mp4 \
  -c:v libx264 -profile:v baseline -level 3.0 -pix_fmt yuv420p \
  -c:a aac -ar 48000 -ac 2 -b:a 128k \
  -movflags +faststart output.mp4
```

## 13. 总结：问题排查速查表

| 用户反馈 | 最可能原因 | 优先检查/解决方向 |
|----------|-----------|-------------------|
| 音画不同步 | PTS 错乱 / 采集时钟漂移 | `ffprobe -show_frames` 检查 PTS，播放器同步模块校准 |
| 画面卡顿 | 解码性能不足 / 网络抖动 | 检查硬解是否启用，查看码率和缓冲区状态 |
| 声音断断续续 | 音频丢包 / jitter buffer 过小 | 开启 FEC/NACK，增大音频缓冲 |
| 画面模糊/马赛克 | 码率过低 / 多次转码 | 提升码率或换 H.265/AV1，检查中间链路是否反复重编码 |
| 播放黑屏/绿屏 | 像素格式错误 / 硬解失败 | 显式指定像素格式，回退软解测试 |
| 首屏慢 | moov 后置 / GOP 过大 | `qt-faststart` 或 `-movflags +faststart`，减小 GOP |
| 发热严重 | CPU 软解/软编高负载 | 切硬解/硬编，降低分辨率或编码预设档位 |
| 直播延迟高 | B 帧 / 切片大 / TCP 缓冲 | 关闭 B 帧，用 RTMP/SRT/WebRTC 替代 HLS |
| 弱网频繁断流 | 码率超带宽 / 无自适应 | 开启 ABR、GCC/BBR 拥塞控制、FEC |
| 回声大 | 扬声器播放被麦克风采集 | 开启 AEC，建议使用耳机 |
