## 1. 编解码技术全景

### 1.1 编解码的本质

编解码是在**信息保真度**、**数据体积**和**计算复杂度**三者之间的系统级权衡。其核心任务包括：
- **冗余消除**：去除空间冗余、时间冗余、统计冗余、感知冗余
- **信息表示**：将原始采样数据映射到更紧凑的码流空间
- **错误恢复**：在有损信道下保证解码质量的可接受性

### 1.2 冗余类型与消除策略

| 冗余类型 | 来源 | 消除策略 |
|----------|------|----------|
| **空间冗余** | 相邻像素高度相关 | 帧内预测 + 变换编码（DCT/DST）+ 量化 |
| **时间冗余** | 相邻帧内容相似 | 运动估计与补偿（ME/MC）+ 帧间预测 |
| **统计冗余** | 符号出现概率不均 | 熵编码（Huffman、算术编码、CABAC） |
| **感知冗余** | 人眼/人耳对某些信息不敏感 | 心理视觉/听觉模型指导的有损量化 |

## 2. 视频编码原理与标准演进

### 2.1 混合编码框架（Hybrid Coding Framework）

现代视频编码器几乎都基于**混合编码框架**，由 MPEG-1/H.261 确立，沿用至今：

```
输入帧
  │
  ├──→ [帧内/帧间预测] → 残差
  │
  ├──→ [变换] → DCT/DST 系数
  │
  ├──→ [量化] → 有损压缩
  │
  ├──→ [熵编码] → 码流输出
  │
  └──→ [反量化+反变换+重建] → 参考帧存储
```

### 2.2 核心模块技术解析

#### 2.2.1 帧内预测（Intra Prediction）
利用空间相关性，根据已编码的相邻像素预测当前块，仅编码预测残差。

- **H.264**：9 种 4×4/8×8 预测模式（DC、Horizontal、Vertical、对角线等）
- **H.265**：35 种预测模式，引入 Planar 预测，支持更大预测单元（PU）
- **AV1**：56 种角度预测 + Filter Intra + Paeth 预测，引入 CfL（Chroma from Luma）
- **VVC**：67 种角度预测 + MRL（多参考行）+ ISP（帧内子分区）

#### 2.2.2 运动估计与补偿（ME/MC）
在参考帧中搜索最相似的块，用运动向量（MV）描述位移，仅编码残差。

**运动估计优化技术**：
- **整像素搜索**：全搜索、三步搜索、钻石搜索、TZSearch（H.265 默认）
- **亚像素搜索**：1/2、1/4、1/8 像素精度，通过插值滤波生成亚像素位置
- **多参考帧**：从多个已解码帧中选择最佳参考
- **双向预测（B 帧）**：同时参考过去和未来的帧

**高级运动补偿**：
- **加权预测（Weighted Prediction）**：处理光照变化
- **OBMC（Overlapped Block Motion Compensation）**：AV1 引入，平滑块边界
- **_affine/6-DOF 运动模型_**：VVC 支持仿射运动补偿，描述旋转、缩放

#### 2.2.3 变换编码
将空间域残差转换到频域，能量集中在低频系数，便于量化和熵编码。

| 标准 | 变换类型 | 特点 |
|------|----------|------|
| H.264 | 4×4/8×8 整数 DCT | 避免浮点误差，16bit 精度 |
| H.265 | 4×4~32×32 整数 DCT + 4×4 DST | DST 用于帧内预测残差，去相关性更强 |
| AV1 | 支持 4×4~64×64，引入 ADST、IDTX | 根据预测模式自适应选择变换核 |
| VVC | 多变换选择（MTS）、子块变换（SBT）| 低频不可分离变换（LFNST）进一步提升压缩效率 |

#### 2.2.4 环路滤波（In-Loop Filter）
在编码/解码环路内对重建帧进行滤波，减少块效应和振铃效应，提升参考帧质量。

- **H.264**：去块滤波器（Deblocking Filter, DBF）
- **H.265**：DBF + SAO（Sample Adaptive Offset）
- **AV1**：DBF + CDEF（Directional Deblocking + Enhancement Filter）+ LR（Loop Restoration，Wiener/Self-Guided）
- **VVC**：DBF + SAO + ALF（Adaptive Loop Filter）

### 2.3 视频编码标准演进路线图

```
H.261 (1990) ──→ MPEG-1 (1993) ──→ MPEG-2/H.262 (1995) ──→ H.263 (1996)
     │                                              │
     │              ┌───────────────────────────────┘
     │              ▼
     │         H.264/AVC (2003) ─────→ MPEG-4 Part 10
     │              │
     │              ▼
     │         H.265/HEVC (2013) ────→ 相比 H.264 节省 50% 码率
     │              │
     │              ▼
     │         AV1 (2018) ───────────→ 开源免版税，Web 主导
     │              │
```

### 2.4 码率控制（Rate Control）

码率控制决定每帧/每宏块分配多少比特，是编码器最复杂的模块之一。

#### 2.4.1 编码模式选择
| 模式 | 原理 | 适用场景 |
|------|------|----------|
| **CBR（Constant Bitrate）** | 恒定目标码率，缓冲区管理严格 | 直播推流、广播 |
| **VBR（Variable Bitrate）** | 根据画面复杂度动态分配码率 | 存储、点播 |
| **CRF（Constant Rate Factor）** | 恒定质量因子，不限制总码率 | 本地转码、归档 |
| **ABR（Average Bitrate）** | 整体平均接近目标，局部可波动 | 兼顾质量和文件大小 |
| **CQ（Constant QP）** | 固定量化参数，码率完全不可控 | 科研测试 |

#### 2.4.2 x264/x265 码率控制算法
- **VBV（Video Buffering Verifier）**：模拟解码器缓冲状态，限制瞬时码率峰值，防止缓冲区上溢/下溢
- **MB-Tree**：基于运动搜索建立宏块代价树，为复杂区域分配更多码率
- **AQ（Adaptive Quantization）**：根据宏块复杂度、边缘、纹理动态调整 QP
- **Lookahead**：分析未来若干帧的复杂度，提前规划 GOP 级码率分配

### 2.5 硬件编解码架构

现代 SoC/GPU 普遍集成专用视频编解码单元（VPU/NVDEC/NVENC/VideoToolbox/MediaCodec），其内部架构通常包括：

```
前端（Front-End）
  ├── 码流解析器（Syntax Parser）
  ├── 运动向量解码器
  └── 熵解码器（CABAC/VLC 硬件加速）

后端（Back-End）
  ├── 逆量化 + 逆变换（IQ/IDCT 专用电路）
  ├── 运动补偿引擎（MC Engine，带片上参考帧缓存）
  ├── 去块/SAO/ALF 滤波器
  └── 像素输出格式化
```

**硬件编码的特点**：
- 延迟极低（通常 < 4ms）
- 功耗远低于 CPU 软编
- 灵活性受限（不能自定义所有参数和算法）
- 质量通常略逊于同码率下的高质量软编

## 3. 音频编码技术

### 3.1 音频编码分类

| 类型 | 代表 | 特点 |
|------|------|------|
| **波形编码** | PCM、ADPCM、AAC、MP3 | 直接编码波形采样，保真度高，码率中高 |
| **参数编码** | LPC、CELP、AMR | 提取语音参数，极低码率，主要用于语音通信 |
| **混合编码** | AAC、Opus、EVS | 结合波形和参数编码优点，现代主流 |

### 3.2 AAC（Advanced Audio Coding）

AAC 是最广泛使用的有损音频编码标准，基于 **MDCT（Modified Discrete Cosine Transform）**。

**核心特性**：
- **时域噪声整形（TNS）**：利用线性预测控制量化噪声的时域分布
- **强度立体声（Intensity Stereo）**：高频段仅编码和声道，差声道用比例因子替代
- **M/S 立体声（Mid/Side Stereo）**：对左右声道不相关时转换为 M/S 编码
- **PS（Parametric Stereo）**：AAC+ 引入，极低码率下用参数描述立体声像
- **SBR（Spectral Band Replication）**：AAC+ 引入，高频用参数重建，节省码率

**编码器比较**：
- **FAAC**：开源，质量一般
- **Fraunhofer FDK AAC**：开源库中质量最优，广泛用于 Android
- **Apple AAC**：业界标杆，质量极佳
- **Nero AAC**：历史知名，现已停止更新

### 3.3 Opus

Opus 是由 IETF 标准化的开源音频编解码器，特别适合**实时通信**。

**技术融合**：
- **SILK**：Skype 开发的语音编码内核，基于线性预测，适合语音
- **CELT**：基于 MDCT 的全频带音乐编码内核
- **混合模式**：自动或手动在 SILK 和 CELT 之间切换

**核心优势**：
- 极低算法延迟（最小 5ms）
- 码率范围极广（6 kbps ~ 510 kbps）
- 全频段支持（8 kHz ~ 48 kHz）
- 内置 FEC 和 DTX（不连续传输）

### 3.4 音频处理链路中的关键技术

| 技术 | 作用 |
|------|------|
| **重采样（Resampling）** | 转换采样率，常用 Sinc 插值或多项式插值 |
| **声道映射/重混音（Remixing）** | 5.1 → stereo、stereo → mono 等转换 |
| **动态范围控制（DRC）** | 压缩音量动态范围，适应嘈杂环境 |
| **元数据嵌入** | Dolby Atmos、DTS:X 的空间音频元数据 |

## 4. 网络传输协议体系

### 4.1 音视频传输协议栈

```
┌─────────────────────────────────────────┐
│  应用层协议：HLS / DASH / RTMP / SRT / WebRTC  │
├─────────────────────────────────────────┤
│  会话/表示层：SDP / SIP / RTSP / WebSocket    │
├─────────────────────────────────────────┤
│  传输层：TCP / UDP / QUIC / SCTP (DataChannel) │
├─────────────────────────────────────────┤
│  网络层：IP / ICMP / IGMP (Multicast)        │
├─────────────────────────────────────────┤
│  链路层：Ethernet / Wi-Fi / 5G NR / LoRa      │
└─────────────────────────────────────────┘
```

### 4.2 TCP vs UDP 在音视频中的取舍

| 特性 | TCP | UDP |
|------|-----|-----|
| **可靠性** | 可靠传输、按序到达 | 尽力而为、可能乱序/丢包 |
| **拥塞控制** | 内置，保守 | 无内置，需应用层实现 |
| **延迟** | 较高（重传、队头阻塞） | 较低 |
| **适用场景** | 点播下载、HLS/DASH、文件传输 | 实时直播、VoIP、视频会议 |

**关键洞察**：
- 点播/短延迟可接受场景：TCP 足够
- 实时交互场景：UDP 更优，配合应用层 FEC、NACK、抖动缓冲
- QUIC 的出现试图在 UDP 上重构 TCP 的可靠性，同时避免队头阻塞

## 5. 流媒体传输协议深度对比

### 5.1 HLS（HTTP Live Streaming）

**Apple 提出，基于 HTTP + TS/fMP4 切片。**

**架构**：
```
源站编码 → 切片服务器（segmenter）→ CDN → 播放器（m3u8 解析 + 顺序下载）
```

**技术细节**：
- **Master Playlist**：描述多码率版本（ABR），播放器根据带宽切换
- **Media Playlist**：按序列号列出 ts/fMP4 切片 URL
- **切片时长**：通常 2~10 秒，影响延迟和切换灵敏度
- **标签扩展**：
  - `#EXT-X-INDEPENDENT-SEGMENTS`：每个切片从 IDR 开始
  - `#EXT-X-DISCONTINUITY`：广告插入/码率切换时的不连续标记

**低延迟 HLS（LL-HLS）**：
- 使用 Partial Segment，将切片进一步细分为 Parts
- 通过 HTTP/2 PUSH 或阻塞加载减少请求往返
- 目标延迟：2~3 秒（相比传统 HLS 的 10~30 秒）

### 5.2 DASH（Dynamic Adaptive Streaming over HTTP）

**MPEG 国际标准，基于 HTTP + fMP4/WebM。**

**与 HLS 的核心差异**：
- 使用 **MPD（Media Presentation Description）** 描述媒体呈现
- 支持更灵活的 **Period/AdaptationSet/Representation/Segment** 层次结构
- 原生支持多种 DRM 方案（PlayReady、Widevine、FairPlay）
- 低延迟 DASH（LL-DASH）使用 `availabilityTimeOffset` 实现 Chunk 级传输

**CMAF（Common Media Application Format）**：
Apple 与 MPEG 共同推动，统一 HLS 和 DASH 的媒体分片格式（fMP4），实现"一份内容，多协议分发"。

### 5.3 RTMP（Real-Time Messaging Protocol）

**Adobe 私有协议，基于 TCP。**

**协议结构**：
- 底层：Chunk Stream 层，将消息分块传输
- 上层： AMF0/AMF3 序列化的命令和数据消息
- 默认端口：1935

**现状**：
- 推流端仍广泛使用（OBS、采集卡）
- 播放端已基本被 HLS/DASH/WebRTC 取代
- 不支持 H.265/AV1，AAC 之外音频支持有限
- 替代品：SRT、RTMPS（RTMP over TLS）、WebRTC 推流

### 5.4 SRT（Secure Reliable Transport）

**Haivision 开源，基于 UDP。**

**核心技术**：
- **ARQ（Automatic Repeat reQuest）**：选择性重传丢失包
- **FEC**：前向纠错，减少重传依赖
- **AES-128/256 加密**：内建安全传输
- **拥塞控制**：基于带宽估计的平滑发送

**技术优势**：
- 在公网弱网环境下比 RTMP 更稳定
- 支持 H.265/AV1
- 单向、双向、多路分发场景都适用

### 5.5 WebRTC

**浏览器原生实时通信框架，基于 UDP + SRTP + SCTP。**

**核心协议栈**：
```
应用层：DataChannel / getUserMedia / RTCPeerConnection
媒体层：RTP / RTCP / SRTP
传输层：UDP / DTLS / ICE / STUN / TURN / SCTP
```

**ICE（Interactive Connectivity Establishment）**：
通过 STUN/TURN 服务器在 NAT/防火墙后建立 P2P 连接，候选类型包括：
- **Host Candidate**：本机 IP
- **Server Reflexive**：通过 STUN 获取的公网映射地址
- **Relay**：通过 TURN 服务器中继

**QoS 机制**：
- **GCC（Google Congestion Control）**：基于延迟梯度 + 丢包率双信号估计带宽
- **NACK + RTX**：接收端请求重传关键包
- **FEC**：ULP FEC、FlexFEC 冗余保护
- **PLC（Packet Loss Concealment）**：音频丢包时的插值/外推补偿
- **Simulcast + SVC**：多路分辨率编码或分层编码，接收端/转发服务器选择最佳层

### 5.6 协议对比总结

| 协议 | 底层 | 典型延迟 | 主要优势 | 主要劣势 | 典型场景 |
|------|------|----------|----------|----------|----------|
| **HLS** | HTTP/TCP | 10~30s | 兼容性强，CDN 友好 | 延迟高 | 移动直播、点播 |
| **LL-HLS** | HTTP/TCP | 2~3s | 兼容 HLS 生态 | 实现复杂 | 低延迟直播 |
| **DASH** | HTTP/TCP | 10~30s | 标准化，DRM 完善 | 延迟高 | 跨平台点播 |
| **LL-DASH** | HTTP/TCP | 2~3s | 标准化低延迟 | 生态不如 LL-HLS | OTT 低延迟 |
| **RTMP** | TCP | 1~3s | 推流生态成熟 | 播放端淘汰，协议老旧 | 主播推流 |
| **SRT** | UDP | 0.5~2s | 弱网稳定，安全 | 生态相对小众 | 户外直播、远程制作 |
| **RTSP/RTP** | UDP/TCP | 0.3~1s | 标准实时协议 | 穿 NAT 困难 | 监控、IPTV |
| **WebRTC** | UDP | < 500ms | 浏览器原生，极低延迟 | 大规模分发成本高 | 视频会议、连麦 |

## 6. 传输层优化技术

### 6.1 前向纠错（FEC）

在发送原始数据的同时发送冗余校验包，接收端在丢包率不超过阈值时无需重传即可恢复数据。

**常见 FEC 方案**：

| 方案 | 原理 | 适用场景 |
|------|------|----------|
| **XOR FEC** | 将 n 个包异或生成 1 个冗余包 | 低丢包率、快速恢复 |
| **RS（Reed-Solomon）** | 基于伽罗瓦域的块码，可恢复任意 m 个丢包 | 固定块大小、确定性恢复 |
| **Raptor / RaptorQ** | 喷泉码，可生成无限冗余包 | 广播、文件分发、DVB-H |
| **FlexFEC** | WebRTC 标准，支持 1D/2D 奇偶校验 | 实时视频通信 |

**FEC 配置权衡**：
- 冗余率越高，抗丢包能力越强，但带宽开销越大
- 实时场景通常配置 10%~30% 冗余

### 6.2 自动重传请求（ARQ）

| 类型 | 机制 | 特点 |
|------|------|------|
| **Stop-and-Wait ARQ** | 发一包等确认 | 简单，效率低 |
| **Go-Back-N ARQ** | 丢包后重传该包及之后所有包 | 实现简单，冗余大 |
| **Selective Repeat ARQ** | 仅重传丢失的包 | 效率最高，缓存要求大 |

**SRT 中的 ARQ**：
采用选择性重传，配合发送端和接收端的滑动窗口和 ACK/NAK 机制，在可控延迟内完成丢包恢复。

### 6.3 拥塞控制

#### TCP 拥塞控制
| 算法 | 特点 |
|------|------|
| **CUBIC** | Linux 默认，基于窗口增长的凸函数，高带宽友好 |
| **BBR** | Google 提出，基于带宽和 RTT 探测，减少 bufferbloat，提升视频启动速度 |
| **Reno/NewReno** | 经典 AIMD 算法，丢包敏感 |

#### 应用层拥塞控制
- **GCC（WebRTC）**：
  - **延迟梯度模块**：通过卡尔曼滤波估计网络排队延迟变化，判断拥塞趋势
  - **丢包模块**：丢包率 > 2% 时主动降码率
  - 两个模块输出取最小值作为目标码率

- **SRT 的 LiveCC**：
  基于 ACK 到达间隔估计可用带宽，平滑调整发送速率

### 6.4 抖动缓冲（Jitter Buffer）

由于网络路由变化，数据包到达时间不均匀。抖动缓冲在接收端暂存数据包，按正确时序和稳定节奏交付解码器。

**设计要点**：
- **静态缓冲**：固定时长，实现简单，适应性差
- **自适应缓冲**：根据 RTT 和抖动动态调整目标缓冲深度
- **隐藏延迟与卡顿的权衡**：缓冲越大越流畅，但延迟越高

### 6.5 QoS 与流量工程

- **DSCP（Differentiated Services Code Point）**：在 IP 头中标记音视频流量为 EF（Expedited Forwarding）或 AF，请求网络设备优先转发
- **DiffServ / IntServ**：区分服务和集成服务模型
- **MPLS TE**：运营商级别的流量工程，为直播大事件预留带宽

## 7. 编解码与网络传输的协同设计

### 7.1 自适应码率（ABR, Adaptive Bitrate）

ABR 是编解码与网络传输协同的最典型体现。核心思想：**网络好的时候发高清，网络差的时候发流畅。**

**实现模式**：

| 模式 | 控制位置 | 特点 |
|------|----------|------|
| **客户端 ABR** | 播放器 | 播放器根据下载速度选择 Representation，HLS/DASH 主流方案 |
| **服务器端 ABR** | 边缘节点/CDN | 服务器根据网络状况选择转发哪一路码率（如 WebRTC Simulcast 的 SFU） |
| **编码端 ABR** | 编码器 | 实时根据带宽反馈调整编码参数（WebRTC GCC → 编码器） |

**ABR 算法**：
- **Throughput-based**：根据过去下载带宽选择档位
- **Buffer-based**：根据播放器缓冲水位选择档位
- **MPC（Model Predictive Control）**：预测未来带宽和缓冲变化，优化长期体验
- **RL-based ABR**：Pensieve（MIT）使用强化学习训练 ABR 策略

### 7.2 GOP 结构与延迟的权衡

**GOP（Group of Pictures）** 直接影响随机访问能力和传输延迟：

| GOP 长度 | 压缩效率 | 随机访问 | 延迟 | 适用场景 |
|----------|----------|----------|------|----------|
| 1s | 中 | 好 | 低 | 直播、互动 |
| 2s | 较高 | 较好 | 中 | 普通直播 |
| 5s+ | 高 | 差 | 高 | 点播、存储 |

**IDR 帧策略**：
- 新用户加入直播、seek 操作、网络恢复后需要 IDR 帧才能开始解码
- 服务器可以通过 **IDR 请求（RTCP FIR/PLI）** 通知编码器立即生成 IDR

### 7.3 错误恢复与关键帧策略

| 技术 | 原理 |
|------|------|
| **周期性 IDR** | 每隔固定间隔发送 IDR 帧，控制错误传播范围 |
| **LTR（Long-Term Reference）** | 保留一个长期参考帧，比 IDR 更小，用于快速恢复 |
| **Intra Refresh** | 将一帧分割为多个条带，逐条带刷新为帧内编码，平滑码率波动 |
| **FMO（Flexible Macroblock Ordering）** | 将宏块交错分配到多个切片中，丢包时利用其他切片恢复（H.264）|
| **SVC 分层编码** | 基础层保证可用，增强层提升质量，丢包时优先保护基础层 |

### 7.4 低延迟编码与传输的配合

要实现端到端延迟 < 1s 的实时系统，编解码和网络必须同时优化：

```
编码侧优化              网络侧优化              播放侧优化
─────────────────────────────────────────────────────────────
关闭 B 帧              UDP / WebRTC            减小 jitter buffer
GOP = 1~2s            减小切片到 1~2s          硬解优先
zerolatency 预设      FEC + NACK               预渲染帧数 = 1~2
slice-based 编码      BBR / GCC 拥塞控制        音频主时钟同步
```

## 8. 现代系统架构实践

### 8.1 直播系统典型架构

```
采集端（OBS / 手机）
    │
    ▼ RTMP / SRT / WebRTC 推流
边缘接入节点（Ingest）
    │
    ├──→ 转码集群（H.264/H.265/AV1，多码率 ABR）
    │
    ├──→ 录制存储（fMP4/TS 落盘）
    │
    └──→ CDN 分发（HLS / DASH / FLV / WebRTC）
                │
                ▼
            全球播放器
```

### 8.2 实时会议系统架构

```
客户端 A  ──┐
            ├──→  SFU（Selective Forwarding Unit）──→ 客户端 B/C/D
客户端 B  ──┘         │
                   MCU（可选，混音/合流）
```

**SFU vs MCU vs Mesh**：

| 架构 | 原理 | 服务器负载 | 客户端负载 | 适用规模 |
|------|------|-----------|-----------|----------|
| **Mesh** | P2P 全连接 | 极低 | 高 | < 4 人 |
| **MCU** | 服务器混音合流 | 高 | 极低 | 大规模直播型会议 |
| **SFU** | 服务器只转发 selected 流 | 中 | 中 | 主流会议方案 |

### 8.3 端到端延迟预算分解

以一场 WebRTC 视频会议为例：

| 环节 | 典型延迟 |
|------|----------|
| 采集 + 预处理 | 10~30 ms |
| 编码（硬编） | 5~20 ms |
| 网络传输（同城市） | 10~30 ms |
| 抖动缓冲 | 30~100 ms |
| 解码（硬解） | 5~15 ms |
| 渲染 | 8~16 ms（1 帧 @60fps） |
| **端到端总计** | **~100~250 ms** |

## 9. 总结

音视频编解码与网络传输是一个高度耦合的系统工程领域：

1. **编解码**的核心是在空间/时间/感知冗余中找到最优压缩路径，现代标准（H.265/AV1/VVC）通过更复杂的预测和变换结构持续提升压缩效率，但计算成本也随之增加。

2. **网络传输**的核心是在不可靠的互联网上实现稳定、低延迟的数据投递。协议选择（HLS/DASH/RTMP/SRT/WebRTC）直接决定了延迟下限和部署成本。

3. **协同设计**决定了用户体验的上限：ABR 动态适配网络、GOP/IDR 策略控制延迟和恢复速度、FEC/ARQ 在带宽和可靠性之间取得平衡。

4. **未来趋势**：
   - 编码侧：AV1 正在取代 H.264 成为 Web 主流，VVC 在专业广播领域渗透
   - 传输侧：WebRTC 向 WHIP/WHEP 标准化推流/播放演进，SRT 在专业制作领域扩张
   - 架构侧：边缘计算 + AI 驱动的超分/降噪/ABR 正在重塑分发链路
